# Discovery — 2026-05-24_2020_auto-fill-placeholder-on-check

## Feature prompt

> Auto-fill checked sets from placeholder. If an exercise's set is checked done with empty weight or reps inputs, the placeholder values become the saved values. This way the user doesn't need to re-type values that are already shown as a placeholder. The placeholder for a set is the previous working-set's logged value (per the existing `useLastWorkingSet` hook), so when the user mimics the previous session and checks the set, the prior weight/reps should auto-commit. Empty AND zero must trigger the auto-fill (an empty input or a literal `0` is what the placeholder is supposed to replace). Only working sets get this behavior; warmups and dropsets are out of scope. Unchecking does not auto-fill (only the check action triggers it).

## Scope summary

Hook the existing per-set "check" handler on the live workout screen so that when the user marks a **working** set as done with empty (or zero) weight/reps inputs, the same `previousSet` values that already render as placeholders get persisted as the row's actual `weight` / `reps`. The placeholder source is already computed (`<ExerciseBlock>`'s `previousByRowId` → `<SetInput>.previousSet` prop) and the persistence path is already wired (`updateSet` partial-spread, fixed in `2026-05-22_1000_set-row-declutter` v3). The change is confined to the live screen's `onToggleSetChecked` callback in `app/(app)/workout/[sessionId].tsx:492-520` — no DB, no schema, no new hook, no API surface change. **Fact (verified):** the `previousByRowId` Map is built on the screen's render tree inside `<ExerciseBlock>`, so the live screen does not currently have direct access to it; the lookup must either be lifted to the screen or the handler must be re-routed through `<ExerciseBlock>` / `<SetInput>` with the previous-set data attached. See Unknowns #1 for the placement call.

## Relevant conventions (verified by reading code)

- **Live-screen handlers `await` mutations.** Every callback inside `<ExerciseBlock>` props on `[sessionId].tsx:443-520` uses `try { await ... } catch (err) { console.warn(...) }`. Pattern: optimism via TanStack `invalidate-on-success`, not via TanStack `optimisticData`. The new auto-fill should follow this — sequence as `await updateSet.mutateAsync(...) → await checkSetM.mutateAsync(id)`, both inside the same try/catch. Failure mode: see Constraints below.
- **Optimistic UI side-effects fire BEFORE the await.** The rest-timer at lines 501-509 is the precedent: `restTimer.start(rest)` fires synchronously before the mutation `await`, with the observer `useEffect` (lines 147-178) as a safety net for races. The auto-fill is **not naturally optimistic** because it writes to the DB and re-renders the input — the local `useState` reset has to happen AFTER the `updateSet` mutation succeeds (otherwise we'd write to the input string state but lose it if the mutation fails). **Designer call**: should the input's local `setWeight`/`setReps` be set synchronously (optimistic) or only after the mutation lands (defensive)? Recommended default: defensive — let the existing `useEffect` on `[row.reps, row.weight, unit]` resync the local state when the cache invalidates. The rest-timer-auto-start retro at `docs/runs/2026-05-22_1415_rest-timer-auto-start/discovery.md:55-58` flagged the same tradeoff and went optimistic; the auto-fill is different because the visible state change is the *input value*, which `useEffect` will pick up automatically on the next cache cycle.
- **`updateSet` is the canonical reps/weight write.** Confirmed by `set-input.tsx:95-100` (commit on blur) and `exercise-block.tsx:243` (onCommit → onUpdateSet → updateSet.mutateAsync). The auto-fill is just another caller of the same mutation with the same patch shape. **No new API surface needed.**
- **"Empty" predicate convention varies by field today.** Inside `set-input.tsx`:
  - `reps`: `parseInt0(s)` returns `null` when `v <= 0` → both `""` and `"0"` collapse to "empty" by this gate.
  - `weight`: `parseFloat0(s)` returns `null` when empty, returns `0` when `"0"` (gate is `v >= 0`) → `""` and `"0"` are DIFFERENT (one becomes `null`, the other becomes `"0.00"`).
  - **Net:** the existing convention treats `"0"` as a valid weight commit but not a valid reps commit. The prompt mandates "empty AND zero must trigger auto-fill" — so the auto-fill predicate diverges from the commit predicate (intentionally). See Unknowns #4.
- **Placeholder source is `previousByRowId.get(s.id) ?? null`** (exercise-block.tsx:235). This is the **fact** Designer must build on. The Map holds: in-session previous set if any, else `lastFromHistory.data`, else `null`. No second source exists — and the prompt's "the placeholder values become the saved values" pins this as the source of truth.
- **`useEffect([row.reps, row.weight, unit])` in `<SetInput>:90-93`** re-syncs local input state from the row. This is the existing pattern for cache-driven input updates. The auto-fill relies on this cycle: updateSet mutation lands → cache invalidates → row.reps/row.weight change → useEffect fires → local `reps`/`weight` strings reset → input re-renders with the new value (replacing the placeholder). **No new wiring needed for the input to "show" the auto-filled value.**
- **`previousSet?.weight` is a `string | null`** (numeric(7,2) on the DB), already in "kg" canonical form. `previousSet?.reps` is `number | null`. The auto-fill patch can just pass these through to `updateSet` directly: `{ weight: previousSet.weight, reps: previousSet.reps }`. No unit conversion needed (the kg-string is the canonical storage form; only the input layer converts between kg and lbs).
- **No e2e test currently asserts the placeholder ON check** — confirmed by grep of `tests/e2e/*.spec.ts` for `placeholder` + `Mark set as completed` (only one match: the `rest-timer-auto-start.spec.ts` and crud.spec.ts:259 which is unrelated). **Tester will add fresh coverage.**
- **No unit test currently exercises the "auto-fill" semantic** — confirmed by grep across `tests/unit/`. The closest negative-space test is `volume-target.test.ts` (asserts the F10 predicate); it would not detect a bug in the new auto-fill path.

## Constraints

- **Data**: no schema change. `sets.weight numeric(7,2)`, `sets.reps integer`, both nullable. RLS unchanged (the existing `auth.uid() = user_id` policy covers the new `updateSet` call). No migration. No cache buster bump.
- **UI**:
  - The set row visual surface is identical before and after the action. After auto-fill commits, the `<TextInput>` re-renders with the auto-filled value as the **value** (not placeholder gray). Net visual: the placeholder gray "100" + green-tint background flip to crisp black "100" + green-tint background. **No new color, no new icon.**
  - **Tap target / interactive surface**: unchanged.
  - **The check-button accessibility label** (`"Mark set as completed"` / `"Unmark set as completed"`) is unchanged. E2E selectors stay byte-identical.
- **Platform**: web + iOS + Android via Expo Router + RN Web. The auto-fill is a pure data-layer + local React state change — no platform-specific code. The same `useState`-cache-invalidation roundtrip works everywhere.
- **Auth**: standard authed session. No change.
- **Performance**: each check action where auto-fill fires now issues TWO PostgREST round-trips (updateSet, then checkSet) instead of one. ~2× cost on the critical path. **Mitigation candidate (out of scope for v1 but worth flagging in Design):** the check path could be expressed as a single `UPDATE sets SET weight = ?, reps = ?, completed_at = now() WHERE id = ?` via a new helper. That's a server-shape change and adds API surface — see Unknowns #2 / Out-of-scope.
- **Failure mode of the new write**: if `updateSet` fails (RLS denial, network) and `checkSet` would otherwise succeed, we have three choices:
  - (a) Abort the entire toggle (don't check). User sees no green tint. Safest.
  - (b) Continue with `checkSet` regardless. User sees a green-tinted row with the original empty/zero weight/reps — the auto-fill "silently failed" but the row is now "checked = committed" under F10 with garbage data.
  - (c) Roll back the check (uncheck) on updateSet failure. Most expensive.
  - **Recommended default: (a)** — match the existing `try { await ... } catch (err) { console.warn(...) }` failure pattern. If updateSet throws, the whole handler bails before checkSet fires. Designer should confirm.
- **The rest-timer auto-start is OPTIMISTIC and fires before the mutations** (`[sessionId].tsx:501-509`). If auto-fill aborts the toggle per (a) above, the timer has already started — visible UX bug. **Mitigation**: move the optimistic timer-start to AFTER the updateSet succeeds (still before checkSet), OR add a `restTimer.stop()` call in the catch branch. **Designer call.** This is the strongest interaction-with-prior-feature flag in the run.

## Unknowns (require Designer judgment or human decision)

1. **Where does the auto-fill logic live?**
   - **(a) Live screen handler (`[sessionId].tsx:492-520`).** Needs access to a per-set `previousSet` lookup, which currently lives inside `<ExerciseBlock>`. Either (i) lift `previousByRowId` to the screen and pass it down (cheaper since both `<ExerciseBlock>` and the screen would consume it), or (ii) add a new `onToggleSetChecked` arg `previousSet?: SetRow | null` populated by `<ExerciseBlock>` from its existing Map.
   - **(b) `<ExerciseBlock>` (close to `previousByRowId`).** Wraps the existing `onToggleSetChecked` prop in a new handler that does the auto-fill + `onUpdateSet` first, then `onToggleSetChecked`. Pro: keeps the placeholder source co-located with the consumer. Con: smears the live-vs-history boundary (history detail mounts `<ExerciseBlock>` without `showCheckable`, so the handler never runs there — but the indirection is harder to reason about).
   - **(c) `<SetInput>` (close to the placeholder values).** Same trade-off as (b) but one layer lower. Pro: `previousSet` is already an in-component prop. Con: `<SetInput>` doesn't own `updateSet` — would need a new `onAutoFill` prop or smash the value into the existing `onCommit`.
   - **Conductor lean: (a)(ii)** — lift `previousByRowId` access via a callback prop. The screen owns the mutation hooks; the block owns the placeholder source. Pass a `getPreviousSet(setId)` callback OR pass the toggled set's `previousSet` in the toggle callback signature. **Designer call.**

2. **Two writes or one combined write?**
   - **(a) Two writes: `updateSet({weight, reps}) → checkSet(id)`.** Simpler, reuses existing API surface, ~2× round-trip cost on the auto-fill path.
   - **(b) New combined helper `checkSetWithValues(id, {weight?, reps?})` that issues a single `UPDATE sets SET weight=?, reps=?, completed_at=now() WHERE id=?`.** One round-trip, but new API surface. Worth doing if the auto-fill ends up being the common case (likely — the prompt's "user mimics the previous session" is exactly the high-frequency flow).
   - **Conductor lean: (a) for v1**, ship the feature with two round-trips. Measure on real iPhone WiFi later; if visibly slow, optimize to (b). **Designer call.**

3. **Optimistic local-input update?** When auto-fill commits, the `<SetInput>`'s local `weight`/`reps` strings are still the user's empty/zero text until the cache invalidates and the `useEffect` resyncs from `row.*`. That's typically <100ms on local Supabase but visible on real-world WiFi. **Options:** (a) defensive — let `useEffect` resync, (b) optimistic — synchronously call `setWeight(...)` and `setReps(...)` from the handler's closure (would need a callback into `<SetInput>` to expose the setters). **Conductor lean: (a)** — the row's green-tint flip from the optimistic timer-overlay/check already provides immediate visual feedback that "something happened"; the input-text catching up half a second later is fine. **Designer call.**

4. **The canonical "needs auto-fill" predicate.** The prompt says "empty AND zero" trigger auto-fill. Verified semantics today:
   - **`row.weight`** is `string | null`. `null` = empty. `"0"` / `"0.00"` = literal zero. A row with `weight = "0.00"` is currently invisible to volume (`weight > 0` filter) and reads as "(blank gray)" because `inputStringFromKg("0.00", "kg") = "0"`. **So the predicate is: `row.weight === null || parseFloat(row.weight) === 0`.**
   - **`row.reps`** is `number | null`. `null` = empty. `0` = literal zero. A row with `reps = 0` is invisible to volume (`reps > 0` filter). **So the predicate is: `row.reps === null || row.reps === 0`.**
   - **Per-field auto-fill or both-or-nothing?** If only `weight` is empty and `reps` is filled, do we (a) auto-fill `weight` only, (b) auto-fill nothing (user clearly partially set this set up — leave it alone), or (c) auto-fill both? **Conductor lean: (a)** — per-field. The user's prompt phrasing ("If an exercise's set is checked done with empty weight or reps inputs") implies any empty input gets the placeholder. Per-field also matches the placeholder UX (each field has its own placeholder). **Designer call.**
   - **What about the input layer's stale local state?** The user might have just typed "5" into reps but not blurred yet. The row's `reps` is still `null` from the cache; the local `reps` state is `"5"`. If we auto-fill from `row.reps == null`, we'd clobber the typed-but-uncommitted "5". **Mitigation**: trigger the input's `commit` (blur-equivalent) BEFORE evaluating the predicate. The check button's `onPress` doesn't currently blur the inputs — adding `Keyboard.dismiss()` or a manual `commit()` call would force the buffered state to land. **Designer call.** Recommended: add a synchronous `commit` call on tap-of-check, then read `row.*` (which will be fresh post-commit), then evaluate the predicate. This is also a low-key win for the existing "tap check without blurring" flow which loses unsaved input today (verified by reading `set-input.tsx` — no blur is forced on check).

5. **What if there's no previous set at all** (`previousSet == null`)? First-ever working set for this exercise across the user's history. Today, the placeholder shows the unit fallback ("kg" / "lbs" / "reps"), and committing an empty set produces `weight = null, reps = null`. **Branch options on check:** (a) silently no-op the auto-fill (proceed to checkSet with nulls; F10 then filters this out of volume — sane), (b) refuse to check (block the action with a console warning, force the user to type values), (c) write `weight = "0", reps = 0` (matches the "empty AND zero must trigger" prompt literally — but the prompt's intent is *backfill from placeholder*, and there IS no placeholder here). **Conductor lean: (a)** — no auto-fill source available, fall through to plain checkSet. The row gets checked with null weight/reps, F10 excludes it from volume, and the user can manually fix it later. Matches existing UX exactly. **Designer call.**

6. **Per-field auto-fill when the previous set has only one of {weight, reps}.** In practice `useLastWorkingSet` requires both (`weight IS NOT NULL AND reps IS NOT NULL`). The in-session fallback at `exercise-block.tsx:112-117` also requires both. **So `previousSet`, when non-null, always has both fields.** No partial-source case to handle. Verified by reading the SQL filter in `getLastWorkingSetForExercise` and the JS filter in `previousByRowId`. **Confirmed not a real unknown** — pinning here for the design doc.

7. **Set type confirmation.** Spec: "only working sets get this behavior; warmups and dropsets are out of scope". Verified by reading `src/db/types.ts:32` (`SetType = "warmup" | "working" | "dropset"`). The toggled set's `set_type` is already checked at `[sessionId].tsx:505` for the rest-timer gate (`toggled?.set_type === "working"`). **Designer should reuse the same check** for the auto-fill gate. **One subtle interaction:** the rest-timer skips warmup AND dropset, matching the prompt.
