# Discovery — 2026-05-22_1415_rest-timer-auto-start

## Feature prompt

> Rest timer can be activated automatically after a set is checked as done. If another set is checked, timer needs to reset. If done set is unchecked, timer keeps going, no action.

Source: `state.md` for this run, mirrored from `docs/features.md:3`.

## Scope summary

Hook the existing `useRestTimer` start trigger into the per-set "check" toggle on the live workout screen. Today the timer auto-starts only when the user taps "+ Working set" / "+ Drop set" (`app/(app)/workout/[sessionId].tsx:362-380`); checking an already-logged set does nothing for the timer. The change is small and scoped to the live screen's `onToggleSetChecked` callback — no DB, no schema, no API surface change. The whole feature lives in one screen file plus a thin tweak to the timer hook contract (idempotent re-`start` resets `endsAt`, which it already does today — re-confirmed below).

## Relevant conventions (verified by reading code)

- **Live-screen handlers `await` mutations.** Every callback inside the `<ExerciseBlock>` props on `[sessionId].tsx:362-421` uses `try { await ... } catch (err) { console.warn(...) }`. Pattern: optimism via TanStack invalidate-on-success, not via optimistic updates. The new auto-start should follow either of two placements (see Unknowns #1); both keep the `await mutateAsync(id)` intact.
- **`restTimer.start` is the only timer mutator visible to the screen.** The overlay separately exposes `stop`, but the screen never calls it. The screen only ever asks the hook to start; the user (via overlay Skip) is the only one who stops. Mirror this — do not call `stop` on uncheck (Q5 confirmed by prompt).
- **`restByExercise.get(ex.id)` returns `undefined` when no routine target.** The existing add-set auto-start (`[sessionId].tsx:374-375`) guards `if (rest && rest > 0)`. Same guard applies to the new trigger. Ad-hoc sessions without a routine: `routineExercisesQ.data` is empty → map is empty → `get(...)` is `undefined` → no auto-start fires. **No default-fallback exists today**; Q6.a defers to Unknowns #2.
- **`useRestTimer` is idempotent on overlapping starts.** Lines 77-86 unconditionally set `endsAt = now + seconds*1000`. Calling `start(90)` while a 60s timer is running with 12s left replaces the state with a fresh 90s window. AsyncStorage is rewritten in the same call. The persisted-end-time design (line 4-21 docblock) means a tab/app restart mid-rest restores from the *latest* `start` call. Reset semantics are free.
- **Accessibility labels** on the check Pressable already convey state: `"Mark set as completed"` / `"Unmark set as completed"` (`src/components/set-input.tsx:117-119`). The auto-start should not require any a11y additions on the row — the timer overlay's existing `accessibilityLabel="Stop rest timer"` (line 64 of overlay) is the surface where the new behavior becomes visible.
- **No tests exist for `useRestTimer` or the rest-timer overlay** (grep of `tests/` for `Rest timer|restTimer|RestTimer|Resting|use-rest-timer` returned zero matches). The Tester will be the first to cover this behavior. Roadmap (`docs/roadmap.md:99`) confirms the timer is intentionally client-side / non-persisted-to-DB.

## Constraints

- **Data**: None new. `sets.completed_at` (already nullable since `2026-05-21_1308_set-check-button`) and `routine_exercises.target_rest_seconds` (`integer?`) are read but not written by this feature. RLS unaffected. No migration. No cache-buster bump (Decision 9, `docs/decisions.md:173-194`).
- **UI**: The `<RestTimerOverlay>` is the only visible surface. Auto-start flips it from idle → running. No new component; no layout changes to set rows. The check button row (`src/components/set-input.tsx:113-128`) gains no new affordance.
- **Platform**: Web + iOS both consume `useRestTimer`. AsyncStorage is the persistence layer on both. No divergence needed. Aux note: on web, the existing tick logic uses `setInterval(250ms)` — fine for both surfaces.
- **Auth**: Standard authed session. No change.
- **Performance**: Each per-set check triggers (a) the existing DB UPDATE round-trip, (b) one `restTimer.start` call which writes to AsyncStorage and bumps two `useState` setters. Negligible. The new trigger does not invalidate any TanStack query — it's pure local state.

## Existing precedents

- **`[sessionId].tsx:373-376` — the post-add-set auto-start.** Same hook, same `restByExercise` map, same guard pattern (`if (rest && rest > 0) restTimer.start(rest)`). The new trigger should be a near-twin: same guard, same call, gated on `nextChecked === true` instead of `set_type !== "warmup"`. This is the **strongest precedent** — the new feature is essentially "do what + Working set does, also on check tap".
- **`src/hooks/use-rest-timer.ts` itself is a precedent** for "start replaces, no separate reset" — `start` is the only mutator. Re-using `start` for the "reset on next check" requirement (Q4) means zero hook surface change.
- **Bulk-check-all-and-finish (`[sessionId].tsx:259-269`) bypasses the per-row toggle handler** — calls `useBulkCheckAllInSession` directly. Precedent for "bulk operations don't share UI side-effects with per-row toggles". This is *why* Q6.b (don't fire on bulk-check) needs no special-casing — the code path naturally diverges.

## Unknowns (require Designer judgment or human decision)

1. **Trigger placement: before or after the mutation resolves?** Two options:
   - **(a) Optimistic** — call `restTimer.start(rest)` synchronously, *before* `await checkSetM.mutateAsync(id)`. Pros: instant timer start matches Strong's perceived snappiness. Cons: if the mutation fails (network, RLS, etc.) the timer runs against a phantom check (the row's `completed_at` stays null; UI rerenders without the green tint).
   - **(b) Post-success** — call `restTimer.start(rest)` *after* the `await` resolves successfully. Pros: timer never "lies"; aligns with the rest of the screen's await-then-invalidate pattern. Cons: tiny added latency (one PostgREST round-trip, sub-100ms typical).
   - **Default recommendation if no further input:** (a) optimistic. Strong starts the timer instantly on tap; a sub-200ms delay would be perceptible on the most frequent action in the session. The phantom-check edge case is rare enough to accept; the user can hit Skip on the overlay if a check fails. But the Designer should pick consciously.

2. **Missing `target_rest_seconds` — silent no-op or default fallback?** When a routine has no rest target for the exercise (or session is ad-hoc with no routine at all), the existing add-set auto-start silently does nothing (`[sessionId].tsx:374-375`). For consistency with that precedent, the new trigger should also silently no-op. **But** the user prompt is general ("can be activated automatically") — they may expect a default like 90s as a fallback. The overlay's `quickStartSeconds = [60, 90, 120, 180]` (`rest-timer-overlay.tsx:16`) suggests 90s as a reasonable default. **Designer call.** Recommended default: silent no-op (match the existing add-set precedent). If a default is desired, propose it explicitly and surface it in Validation.

3. **Should the auto-start preempt a manually-started timer?** Today the user can tap any of `[60, 90, 120, 180]` quick-start buttons (`rest-timer-overlay.tsx:25-37`) to fire `start(s)` directly. If the user manually starts a 180s timer, then checks a set on an exercise with `target_rest_seconds = 60`, the new trigger will replace the 180s timer with a 60s one (because `start` overwrites). Is that the intended UX, or should the trigger respect a running timer and only auto-start when idle? **Designer call.** The prompt says "If another set is checked, timer needs to reset" — which implies overwrite-on-check is the desired UX. By the principle of consistency, the same overwrite likely applies whether the previous start was manual or auto. **Default recommendation: always overwrite (mirror Q4 semantics for any in-flight timer source).**

4. **Re-checking the same set — fire again or no-op?** The toggle is bidirectional. If the user taps a checked set (uncheck, no timer action per Q5), then taps it again (re-check), should the timer fire fresh? By the prompt's literal wording, yes — every transition from unchecked → checked starts the timer. The handler already discriminates on `nextChecked === true`, so this falls out for free. **Worth confirming in Design** but not a real ambiguity.

5. **What about cross-exercise timer reset?** Spec wording is "If another set is checked, timer needs to reset". Interpreted broadly: any set, any exercise. The `restByExercise.get(ex.id)` lookup naturally uses the *new* set's exercise's target_rest_seconds — which could be larger, smaller, or undefined relative to the previous trigger. Designer should pin: (a) always overwrite with the new exercise's rest_seconds; (b) if the new exercise has no target, silently no-op (do not stop the running timer) or stop it. Recommendation: **(a) overwrite with the new exercise's seconds when present; if undefined, leave the existing timer untouched** (don't punish a between-exercises check by killing the user's current rest). This is a non-trivial UX call that should be explicit in the design.

6. **Warmup sets — should auto-start fire?** The existing add-set auto-start (`[sessionId].tsx:373`) explicitly skips warmups (`if (input.set_type !== "warmup")`). Checking a warmup set is a real flow (user does warmups, taps check to mark them done). Should the timer fire? Strict consistency with add-set says no; literal reading of the prompt says yes (no exception for warmups). **Designer call.** Recommendation: **skip warmups** — they're explicitly tagged in the data model and the existing precedent treats them as not-rest-worthy. Bonus: the `row.set_type` is already available on the SetInput row and could be threaded through `onToggleChecked` if needed, or fetched from the set via the screen's `setsByExercise` lookup in the handler.

7. **Drop sets — should auto-start fire?** Dropsets are chained to a parent working set and represent a single rest period after the chain finishes. The existing add-set auto-start treats them like working (auto-start on add). For check, the same logic likely applies: rest only matters after the *last* drop set in a chain, not after each. But discriminating "is this the last drop in a chain?" inside the handler adds complexity. **Designer call.** Recommendation: **fire on every checked dropset just like working** — same as add-set precedent. Worst case: the timer resets when the user checks the next drop in the same chain (Q4 semantics), which is fine.

## Out-of-scope flags

- **Native push / haptic / sound when the timer ends.** Mentioned as future work in `docs/iphone-shakedown.md:36` and `docs/roadmap.md:132`. Explicitly out — the prompt asks only for auto-start on check.
- **A UI affordance for opting out per-exercise** (e.g., "no rest after this exercise's sets"). Not in scope; if needed later, would extend `target_rest_seconds = 0` semantics.
- **Per-set rest seconds override** (different rest after working vs. warmup vs. drop within the same exercise). Not in scope; only one `target_rest_seconds` per (routine, exercise).
- **Changing the data model** (no migration, no new columns). Confirmed: all needed values already flow through `restByExercise`.
- **Modifying `<RestTimerOverlay>`'s visual or quick-start buttons.** The overlay is a passive subscriber; it re-renders automatically when `useRestTimer` updates. No prop changes.
- **Tests for the pre-existing add-set auto-start.** Backfilling that gap is tempting but not in scope. New tests for this feature focus on check→start, check-different-set→reset, uncheck→no-op.
- **Skip-button behavior changes.** The overlay's Skip already calls `stop` on the same hook instance; nothing changes about that flow.
