# Discovery — 2026-05-23_1855_read-only-history-view

## Feature prompt
Read-only history view. When accessing a workout through the history page, the user can currently change values and delete/add sets and exercises immediately — this shouldn't be the default. We need a history view that is read-only by default, with an explicit "Edit" button on the workout that enables all fields to be edited. The read-only view should be a new component. Editing the start/end times via the existing pencil flow remains as-is (it's already gated by tap-to-reveal); this feature is about the body of the workout (exercises, sets, weights, reps, checkmarks, RPE, notes).

## Scope summary
The history detail screen (`app/(app)/history/[id].tsx`) currently renders ended workouts using the exact same `<ExerciseBlock>` + `<SetInput>` primitives as the live workout. Every set field is a live `<TextInput>`, the trash icon is always present, an "+ Working set" button is always available, and "Add exercise" / "Delete workout" are always available too. The session name is also an always-editable `<TextInput>`. This run introduces a default read-only mode for the body of an ended workout, with an explicit "Edit" toggle that flips into the current behavior. The `<SessionTimesEditor>` pencil flow is already gated by tap-to-reveal and stays untouched.

## Relevant conventions (verified by reading code)
- **Primitive reuse over forking**: `<ExerciseBlock>` already toggles behavior between live and history via boolean props (`showCheckable`, `showVolumeTarget`, plus conditional handlers — `onMoveUp`/`onMoveDown`/`onRemove`). Adding a read-only mode by the same pattern (e.g. a `readOnly` prop, OR by simply omitting handlers and having the block render text instead of inputs) is consistent with the codebase. The prompt asks for "a new component" specifically for the read-only view, so the implementer should choose: (a) a new `<ExerciseBlockReadOnly>` (clean fork), or (b) extend `<ExerciseBlock>` with a `readOnly` prop that hard-swaps `<TextInput>` → `<Text>`. Designer decision.
- **View → Edit precedent**: `app/(app)/measurements/[id]/index.tsx:120-129, 145-154` — a Pressable Pencil in `Stack.Screen.headerRight` PLUS a wider "Edit measurement" button at the bottom, both navigating to `/measurements/[id]/edit`. That precedent uses **two screens, not in-place toggling**. The exercise progress→edit precedent (`exercises/[id]/progress.tsx:48-65` → `exercises/[id]/index.tsx`) is the same pattern. Neither precedent applies "in-place flip" — both go to a separate edit route.
- **In-place tap-to-reveal precedent**: `<SessionTimesEditor>` (session-times-editor.tsx:113-133) shows read-only summary + Pencil icon; tap reveals editor; explicit Save / Cancel buttons; closes via `useEffect` watching `isSubmitting` true→false. This is the closest in-place precedent and the one the prompt evokes ("editing the start/end times via the existing pencil flow remains as-is").
- **Header button precedent**: `Stack.Screen.headerRight` with a Pressable Pencil + `accessibilityLabel` is the dominant header-pencil pattern (measurements view, exercises/progress) — both use `color={colorScheme === "dark" ? "#fff" : "#000"} size={20}`.
- **Mutation hook contract**: every `use*` set/session mutation invalidates `["sets", sessionId]` and/or `["sessions", ...]` + `["stats"]` + `["progress"]`. Read-only mode invokes nothing → no cache changes during a session view, which is desirable.
- **In-progress session redirect** (history/[id].tsx:70-74): `if (session.data && !session.data.ended_at) router.replace('/(app)/workout/${id}')`. This means the route `/history/[id]` for an in-progress session BOUNCES to the live screen unconditionally — the new read-only mode therefore applies only to ended sessions in practice. Confirmed.
- **TanStack Query + RLS** are the standard data path; no Drizzle on this surface.
- **NativeWind className** patterns: borders `border-b border-gray-200 dark:border-gray-800`, neutral text on `bg-white dark:bg-black`, inputs `rounded border border-gray-200 px-2 py-1.5 ... dark:border-gray-800`.

## Constraints
- **Data**: No schema changes. RLS-protected `sessions` and `sets` tables. Read-only mode is a pure client-side gating concern.
- **UI**: The screen is rendered inside an Expo Router `Stack`, so `Stack.Screen.headerRight` is the canonical place for a header-level Edit button. The `<SessionTimesEditor>` MUST keep its tap-to-reveal pencil even in default read-only mode (per prompt). The "Delete workout" red button at the bottom and the session-name `<TextInput>` both currently render unconditionally — Designer must decide whether they fall under the new Edit toggle or stay independent (see Unknowns).
- **Platform**: Web (Playwright is the e2e gate) + iOS + Android. RN `<TextInput editable={false}>` doesn't visually distinguish on web/native unless paired with a className change; if the read-only mode uses `<Text>` instead, it removes ambiguity. The check buttons (`showCheckable`) are not passed on history today anyway.
- **Auth**: Same user-scoped RLS — no changes.
- **Performance**: Read-only mode strictly removes interactivity; no new queries; the existing `useAllExercises` + `useSetsForSession` queries continue to drive what's shown. The 30s `staleTime` persisted query behavior carries over.

## Existing precedents
- **`<SessionTimesEditor>`** (`src/components/session-times-editor.tsx:57-133`) — the gold-standard in-place "default read-only, tap pencil to edit, Save/Cancel" pattern in this codebase. The new body Edit toggle has two viable shapes derived from this precedent:
  1. **Header-pencil (one toggle for the whole body)**: a Pencil in `Stack.Screen.headerRight` flips a screen-level `editing` state. Mirrors `<SessionTimesEditor>` semantics but at screen scope. Closest to "Edit button on the workout" phrasing in the prompt.
  2. **Measurements-style separate route** (`app/(app)/measurements/[id]/edit.tsx`) — push a new route for the edit screen. More effort, doesn't match the prompt's "edit button on the workout" phrasing as well, and would split the time-edit pencil from the body editor (they'd live on different screens).
  Designer recommendation: option 1, but final call is Designer's.
- **`<ExerciseBlock>`'s `showCheckable` + `showVolumeTarget` toggle pattern** (exercise-block.tsx:36-44, 64) — established way to vary behavior between live and history without forking. Read-only mode can extend this with a `readOnly` prop or with a new sibling component.
- **`onRemove` / `onMoveUp` / `onMoveDown` omission pattern** (exercise-block.tsx:124, "showActions = !!onMoveUp || !!onMoveDown || !!onRemove") — when callers omit these handlers, the corresponding action row is fully hidden. Read-only mode can extend this by ALSO omitting `onAddSet` / `onUpdateSet` / `onUpdateSetMeta` / `onDeleteSet`, but then the prop contract changes from required → optional and many edge cases (the "+ Working set" footer that uses local `isAddingSet` state, the per-row Trash button, the SetRowMenu trigger) all have to gate on those.
- **Header layout idiom**: measurements (`measurements/[id]/index.tsx:145-154`) and exercises progress (`exercises/[id]/progress.tsx:48-65`) both use a Pencil in `Stack.Screen.headerRight` with `accessibilityLabel="Edit X"`, `color` driven by `useColorScheme()`, `size={20}`. That's the established pattern for "tap pencil to edit".
- **Two-button row precedent for Save/Cancel** (`session-times-editor.tsx:207-224`): a `<View className="mt-1 flex-row gap-2">` with two `flex-1` Buttons (`primary` + `secondary`). Reusable if the read-only flip uses an explicit "Done" or "Save changes" exit.

## Unknowns (require Designer judgment or human decision)
1. **What exactly is "read-only"** — the prompt says "fields cannot be changed" and lists "exercises, sets, weights, reps, checkmarks, RPE, notes". Options:
   - (a) Swap `<TextInput>` → `<Text>` showing the formatted value, hide trash icons, hide "+ Working set" footer, hide "Add exercise" button, hide "Delete workout" button. Most explicit; produces a visually different surface.
   - (b) Set `editable={false}` on `<TextInput>` and disable Pressables. Cheaper but visually ambiguous (the inputs still look like inputs).
   - The prompt's "The read-only view should be a new component" leans toward (a) — a structurally distinct component rather than a gated version of `<ExerciseBlock>`.
2. **Exit path from edit mode** — the prompt says "an explicit Edit button … enables all fields to be edited". It does NOT specify how to exit. Options:
   - (a) "Done" button in `headerRight` while editing (mirrors the pencil-as-Done convention).
   - (b) Auto-exit on navigate away; no explicit exit (lightest, but worst affordance).
   - (c) Save/Cancel pair (mirrors `<SessionTimesEditor>`, but here every edit is already auto-committed on blur, so "Cancel" would have to also undo mutations — adds complexity not implied by the prompt).
3. **Session-name TextInput + "Delete workout" button + "Add exercise" Pressable** are all part of the screen body but not part of the per-exercise blocks. Should they ALSO be gated behind the new Edit toggle? The prompt explicitly lists "exercises, sets, weights, reps, checkmarks, RPE, notes" — which INCLUDES the structural set "exercises" (implying add/remove of exercises is in scope). Session-name and Delete-workout are arguable. Designer should decide. Suggested default: name + delete + add-exercise all gated by Edit; only `<SessionTimesEditor>` stays independent (per prompt).
4. **In-progress sessions** — `app/(app)/history/[id].tsx:70-74` already redirects in-progress sessions to `/workout/[id]`. So the read-only mode applies only to ended sessions in practice — no extra handling needed unless the redirect is intentionally removed (no signal in the prompt that it should be).
5. **Per-screen vs per-block edit scope** — does tapping Edit unlock the whole workout (all exercises at once), or one block at a time? The prompt's phrasing ("Edit button on the workout") points to per-screen. Designer call.
6. **Does the time-edit pencil stay independent in BOTH modes?** Prompt is explicit: yes. But the implementer should verify that when the body is in read-only mode, the time-edit pencil is still tappable, and when the body is in edit mode, the time-edit pencil flow doesn't interfere (e.g. no double-confirm UX).
7. **Does the route also serve as a passthrough for the verdict screen redirect path?** `/workout/verdict/[sessionId].tsx` is separate; users only land on `/history/[id]` from the history list (`history/index.tsx:53`) and the week drill-down (`history/week/[isoWeek].tsx:200`). Both are post-finish entries. Confirmed.
8. **e2e coverage of the current "editable from history" behavior**: I found NO Playwright spec that taps a set on history detail to change a value, add a set, delete a set, edit RPE, or edit notes. The only history-detail spec arms in `tests/e2e/crud.spec.ts:215-393` exercise the time-edit pencil. `tests/e2e/soft-deleted-exercises-in-history.spec.ts` only asserts presence of blocks + the "(deleted)" suffix. `tests/e2e/remove-exercise.spec.ts:174-186` actively asserts trash icons have count 0 on history detail. `tests/e2e/volume-target.spec.ts:579-601` asserts the volume-target strip is absent. Therefore: **no existing e2e arm needs to be updated to "go through the Edit button"** — the editability was de facto, not under test. The Tester step should ADD new arms that prove (i) fields are read-only by default and (ii) tapping Edit re-enables them.

## Out-of-scope flags
- **No changes to `<SessionTimesEditor>`** — its tap-to-reveal pencil flow stays exactly as today (explicit prompt directive).
- **No changes to the live workout screen** (`app/(app)/workout/[sessionId].tsx`) — it must keep all current editability.
- **No new mutation hooks**, no new API endpoints, no schema changes.
- **No undo/redo or pending-changes diffing** — every existing mutation auto-commits on blur. Read-only mode just gates entry to those mutations.
- **No changes to the in-progress→live redirect** (history/[id].tsx:70-74). Read-only mode only ever applies to ended sessions because of this redirect.
- **No FAB / no sticky bottom button** for the Edit toggle — codebase precedent is a header Pencil, not a FAB. Stay with the precedent.
- **No per-set or per-exercise inline Edit toggles** — the prompt is about an Edit button on the workout (singular).
- **Do not invent new acc'y labels off-pattern** — reuse the `accessibilityLabel="Edit X"` shape from `measurements/[id]/index.tsx` and `exercises/[id]/progress.tsx`.
