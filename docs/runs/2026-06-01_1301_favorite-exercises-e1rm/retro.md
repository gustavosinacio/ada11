## Systemic lesson (the highest-value finding for the playbook)

**The e2e convention should codify "after an optimistic mutation, return to the asserting screen via CLIENT-SIDE nav + `waitForResponse` on the mutation, never `page.goto`."** This run's round-1 FAIL and the prior fix run's (`2026-06-01_0941_session-finish-exercise-order`) round-2 de-flake were the SAME root cause: an authored e2e returns to a screen via `page.goto` (a HARD browser reload), which (a) races the in-flight optimistic-write network call and (b) rehydrates a STALE query cache from `PersistQueryClientProvider` AsyncStorage (30s `staleTime` + persist-throttle) without a refetch. A real user always navigates client-side (tab tap / in-app back), so the in-memory cache is preserved and the race never manifests — the bug is purely in how the test models navigation.

This is now at least the 2nd run where a hard-reload/`page.goto` return raced an optimistic write. The fix shape is identical both times:
1. `await Promise.all([page.waitForResponse(<mutation POST/DELETE>, status<300), <toggle>.click()])` so the write lands server-side before navigation.
2. Return to the asserting screen via a client-side tab tap (`page.getByText("<Tab>", { exact: true }).first().click()` + `page.waitForURL`), NOT `page.goto`.

`page.goto` is correct ONLY for the initial landing and for deep-links to a fresh screen (no preceding optimistic mutation) — both of which this spec correctly kept (`favorite-exercises-e1rm.spec.ts:217,229,280`).

**Recommendation:** add to the e2e authoring convention (project README / Tester + Implementer agent definitions): "An e2e that asserts the result of an optimistic mutation on another screen MUST (1) `waitForResponse` on the mutation before navigating, and (2) return via client-side nav, not `page.goto`. Reserve `page.goto` for initial loads and mutation-free deep-links." Codifying this would have pre-empted BOTH runs' final round.
