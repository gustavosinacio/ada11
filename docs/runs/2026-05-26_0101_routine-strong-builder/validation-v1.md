## Issues found

### Blockers

### Majors

- **[MAJ-1]** `design-v1.md:509-553` (Pre-seed at session-create → step 4 / "Refinement (cleaner)" block): the design carries an internal contradiction across two code blocks. Step 4 first introduces `parentNaturalKeyByRoutineSetId` and starts populating it in a loop with a comment "actually we capture this in pass 0 by indexing the built rows", then immediately defines a different map `routineSetIdToNaturalKey` in the "Refinement (cleaner)" subsection. Pass 2 (step 5) only uses `routineSetIdToNaturalKey`. The first loop is dead code that an Implementer is likely to retain. **This must be cleaned up before implementation** — pick exactly one map name, populate it inside step 3 (alongside the row builders), drop the post-pass-1 reconstruction loop entirely. Suggested fix: rewrite step 3's pseudo-code so `routineSetIdToNaturalKey.set(rs.id, \`${exId}:${nextNumber}\`)` is the SINGLE place this map is populated (regardless of set_type), then strip step 4's vestigial loop.

- **[MAJ-2]** `design-v1.md:328-336, 591-601` (Seed failure rollback policy): the chosen policy ("log + proceed, no rollback") combined with the only error surface being `console.warn` produces a silent-failure UX. The live screen mounts with empty seeded state but populated `routine_exercises`, so the user sees exercise blocks with zero sets and no signal that seeding was supposed to happen. The design's counterpoint flag acknowledges this but defers to "future toast/banner out of scope". I disagree with the calibration: this is not future polish, it's the v1 path's only error surface. Two minimum bars must be met before this is mergeable: (a) the mutation either throws (so the existing `try/catch` in `workout/index.tsx:62-64` keeps the user on the routine list with a console error and `router.replace` doesn't fire), OR (b) the live screen shows an explicit "Couldn't load this routine's sets — add them manually or restart" banner above the first empty exercise block when `session.routine_id != null && setsQ.data?.length === 0`. Suggested fix: choose (a) for v1 — the simplest behavior change is removing the `try/catch` around `seedSetsForSession` so a failure rejects the mutation, the user stays on workout/index.tsx, and the existing `console.warn("Start failed", err)` path fires. The orphan session row is fine — it shows up in History as in-progress.

- **[MAJ-3]** `design-v1.md:472-475, 463-466` (idempotency guard + duplicate-exercise-in-routine): the design assumes the natural key `(exercise_id, set_number)` is unique across all rows produced by the seed because "a routine has at most one routine_exercise per exercise". This is **not enforced** at the DB level — no `(routine_id, exercise_id)` unique index exists (only `(routine_id, position)` per `0012`). Soft-delete-then-readd, admin-seed paths, and the existing race spec (`routines-add-exercise-race.spec.ts`) all describe paths where two non-deleted `routine_exercise` rows can carry the same `exercise_id`. Under the design's `setNumberByExercise` algorithm, this still produces unique `(exId, setNumber)` keys (numbers monotonically increment across all routine_exercises sharing an exercise_id), so the seed's bulk insert succeeds. BUT the idempotency guard at step 2 (`skipExerciseIds.has(exId)`) skips the entire exercise on retry, including legitimate not-yet-seeded routine_exercises. The retry semantics are degraded. Suggested fix: either (a) document explicitly that v1 trusts the picker-level dedupe and doesn't aim to support duplicate-exercise-in-routine semantics on seed (acceptable since it matches the live-screen's existing `seen` set dedupe at `workout/[sessionId].tsx:190-199`), AND tighten the idempotency guard to track at the `(session_id, exercise_id, set_number)` tuple instead of exercise_id alone; or (b) add a DB-level partial unique on `(routine_id, exercise_id) WHERE deleted_at IS NULL` in the same migration. Option (a) is cheaper and consistent with the live-screen invariant.

### Minors

- **[MIN-1]** `design-v1.md:351-365` (`<RoutineExerciseCard>` props): the `RoutineExerciseSetEntry` type is mentioned at the `src/db/types.ts` row in the file changes table ("RoutineExerciseSetEntry (= row with optional joined exercise — not required if API uses parallel fetch; finalized below)") but never finalized below. Designer should explicitly state "not added — parallel fetch is the chosen path; `<RoutineExerciseCard>` receives `entry: RoutineExerciseEntry` (existing) + `setsForExercise: RoutineExerciseSetRow[]` (new), no joined type needed". Suggested fix: replace the prose with a one-line decision.

- **[MIN-2]** `design-v1.md:28-29` (`src/db/schema.ts` entry for `routineExerciseSets`): the bullet says "Add `routineExerciseSets` table mirroring SQL (UUID PK, FKs, `setNumber`, `setType` text + CHECK, `targetReps`, `targetWeight` numeric(6,2), `parentSetId` self-FK `set null`, `notes`, timestamps, dropset CHECK invariant)" but doesn't spell out the two Drizzle `check()` builder entries verbatim. The `sets` precedent at `schema.ts:175-183` has BOTH `setTypeCheck` and `parentInvariant` — Implementer needs both. Suggested fix: in the same v2 pass that addresses MAJ-1, include the two `check()` blocks verbatim in the design's "Drizzle schema" subsection (which doesn't currently exist — promote it from a single bullet to a labeled subsection with code).

- **[MIN-3]** `design-v1.md:393-396` (confirm-delete predicate on row trash): "Confirms via `confirmDelete` only if the set has `target_reps != null && target_weight != null`" is documented only in the Layout subsection, not in the props contract. Suggested fix: either (a) lift it to a named prop on `<RoutineExerciseCard>` (e.g. `onConfirmRemoveSet?`) so the component owns the decision; or (b) inline a footnote in the props block that the trash callback may show a confirm before invoking `onRemoveSet`. Clarifies who owns the gesture.

- **[MIN-4]** `design-v1.md:701-708` (migration backfill SQL tests): designer hedges "If infra doesn't support that, fold into tests/rls.test.ts setup phase as a pre-flight assertion". The hedge is fine but the fallback should be the default — `tests/migration-backfill.test.ts` is a new test file with no existing vitest/jest harness in the repo (the only TS test files at top-level are `tests/rls.test.ts` and `tests/seed-and-auth.test.ts`, both `main()`-script style, not vitest). Suggested fix: re-anchor backfill assertions as a section appended to `rls.test.ts` (or, cleaner, a sibling `tests/migration-backfill.ts` script run via the same npm-test runner). Don't introduce a vitest/jest dependency for one feature.

- **[MIN-5]** `design-v1.md:419-421` ("optional spinner via `pendingRoutineId === r.id`"): the design defers per-row spinner styling to "later". `<RoutineListItem>` already exposes `disabled={hasActive}` (verified at `routines-add-exercise-race.spec.ts` references). Suggested fix: spec the `pending` prop on `<RoutineListItem>` explicitly even if it just forwards to the existing disabled visual — Implementer otherwise won't know whether to extend the props or not.

- **[MIN-6]** `design-v1.md:264-272` (single PostgREST embed call for `listRoutineExerciseSetsForRoutine`): the snippet uses `.select("*, routine_exercises!inner(routine_id)")` to filter via dotted path. This works, but it ships `routine_exercises.routine_id` as a column in the returned rows. The post-processing should drop it before exposing as `RoutineExerciseSetRow[]` — the typed row shape doesn't carry that field. Either spec the stripping (mirror `getLastWorkingSetForExercise`'s `const { sessions: _sessions, ...row } = data` pattern at `sets.ts:200-203`) or extend the row type to optionally carry the embed.

- **[MIN-7]** `design-v1.md:439-450` (seed step's `routine_exercises.deleted_at IS NULL` filter): the design correctly filters via `.is("routine_exercises.deleted_at", null)`. But the design does NOT also filter the `routine_exercise_sets.deleted_at` cascade — soft-deleted routine_exercises rows that still have non-deleted `routine_exercise_sets` rows would have their sets seeded into the new session (because the inner-join keeps the row alive on the right side). Suggested fix: also add `.is("deleted_at", null)` on the `routine_exercise_sets` level (already present at line 448) AND keep the routine_exercises filter. Cross-check: does soft-deleting a routine_exercise cascade-soft-delete its routine_exercise_sets? It doesn't (cascade is ON DELETE in Postgres, not on soft-delete). So this is a real edge case: if a user soft-deletes an exercise from a routine, the orphan routine_exercise_sets remain non-deleted. The current filter actually handles this correctly because `routine_exercises!inner` requires a JOIN — a soft-deleted parent excluded by `.is("routine_exercises.deleted_at", null)` would also exclude its child rows from the result. **Verified the filter is sufficient.** Re-classify this MIN as informational: design is correct; consider adding a comment in the SQL block of `seedSetsForSession` calling out this reliance on inner-join filter semantics.

- **[MIN-8]** `design-v1.md:330-334` (the `console.warn("Seed failed", err)` line): if MAJ-2 is resolved by removing the try/catch entirely, this MIN dissolves. Otherwise, the message should include the routine_id for triage (`console.warn("Seed failed for routine", input.routine_id, err)`).

## Decision

**no-go**

Reasoning:
- 3 majors, no blockers. Playbook rule "0 blockers + ≤1 major → go, else no-go" → no-go.
- MAJ-1 is a clarity issue Designer can resolve in v2 with a focused rewrite of the two-pass section.
- MAJ-2 needs a deliberate UX call from the Designer (or escalation to Conductor/human). My recommendation is "fail loudly" (remove try/catch, let mutation reject) — cheaper than a banner, consistent with the existing `console.warn("Start failed", err)` path.
- MAJ-3 is the most subtle: the duplicate-exercise-in-routine path is real but the current code's UI dedupe (live screen + picker excludeIds) already papers over it. Document the assumption explicitly OR add the DB constraint. Either is acceptable.
- Minors MIN-1..MIN-8 can all be folded into the v2 pass.

Recommendation to Conductor: invoke Designer for design-v2 addressing MAJ-1/MAJ-2/MAJ-3 + the minors. One round should be sufficient; no need to escalate to budget-exhausted.
