### Majors

- **[MAJ-1]** design-v1.md "Test plan handoff" table + AC7 mapping: AC4 ("badge renders") and AC5 ("forced API call rejected by RLS + no UI affordance") are partially deferred to Tester. The plan names `tests/rls.test.ts` arms 4-6 for the API rejection (good), but the chip-renders-on-user-owned-only and pencil-absent-on-canonical assertions are described as "Tester decides shape — either a new `tests/e2e/canonical-exercise-gating.spec.ts` or extension of `crud.spec.ts`". State.md AC7 explicitly requires "Tests added for: ... badge rendering, edit/delete gating". The contract from the playbook is that the Designer specifies WHAT each test must assert; Tester executes. The design should pin: (a) whether a new spec is created or `crud.spec.ts` is extended, (b) the exact assertions (e.g., "after `createExercise({...})`, navigate to /exercises and assert `getByText("You")` exists on the new row; navigate to a canonical row's progress page and assert `getByLabel("Edit exercise")` is absent; navigate to `/exercises/<canonical-id>` directly and assert the Save button text is absent and a Back button is present"), (c) test-user setup (existing pattern from `auto-fill-placeholder-on-check.spec.ts` etc.). Without pinning, the Tester round may produce thin or wrong coverage. **Suggested fix**: add a "New e2e: `tests/e2e/canonical-exercise-gating.spec.ts`" subsection under "New artifacts" with: spec body outline, four named test cases (chip-on-own, no-chip-on-canonical, no-pencil-on-canonical-progress, deep-link-read-only-screen), and the exact Playwright locator strategy (accessibilityLabel + getByText). 1-2 paragraphs is enough; this is a Designer-owned contract, not a Tester-owned one.

### Minors

- **[MIN-1]** design-v1.md "Mudanças por arquivo" row for `app/(app)/exercises/[id]/index.tsx:31-208` says: "Form state (useForm, zodResolver) is gated behind `data?.user_id != null` to avoid a wasted controller mount". The "Edit-screen read-only shape" section (L186-215) contradicts: "useForm still mounts (cheap, harmless) — gating it would add a hook-ordering risk; the read-only branch just doesn't reach the Controllers." The latter is correct (gating a hook by data-conditional value is a hook-order violation); the former is wrong. **Suggested fix**: remove "Form state ... is gated behind `data?.user_id != null`" from the file-changes table; replace with "Form state (useForm, zodResolver) stays mounted unconditionally; the read-only branch just doesn't render the Controllers." Implementer disambiguation.

- **[MIN-2]** design-v1.md "Helper contract" docstring: "The `admin` client is required because RLS still hides soft-deleted rows from the anon client". This is wrong — soft-delete is a client-side filter (`.is("deleted_at", null)` in `src/api/exercises.ts:15`), not enforced by RLS. The post-migration SELECT policy is `user_id IS NULL OR auth.uid() = user_id`, no `deleted_at` term. An authenticated user client could read soft-deleted canonical rows; the helper using admin is still correct (for predictability across tests), but the justification in the comment is wrong. **Suggested fix**: replace the rationale with "Convention: tests read setup data via admin; switching to a user client would change the implicit contract and require sign-in plumbing." Same outcome, accurate reasoning.

- **[MIN-3]** design-v1.md "Risks 1" claim: "Supabase CLI wraps each file in `BEGIN ... COMMIT` automatically". This is accurate for the new `supabase/migrations/` push path used here, but the design should also note that the existing on-Supabase remote DB applies migrations via `npx supabase db push` (per `docs/development.md:111`) which uses the migration runner's transaction wrapper. The risk is unchanged; just calling out the load-bearing tooling assumption helps the Implementer pick the right deploy command. **Suggested fix**: 1-line note in the migration's header comment ("Single-file txn; apply via `npm run db:push`.").

- **[MIN-4]** `canEdit = exercise.data?.user_id != null` evaluates to `false` while `data` is undefined (during the loading phase). Today the pencil is unconditionally rendered (visible during loading). Post-design, the pencil briefly disappears during the loading window even for user-owned rows, then reappears. Functional regression is bounded (<1s on a fresh navigation); cosmetic. **Suggested fix**: optional — let `canEdit` short-circuit on loading via `exercise.isLoading || exercise.data?.user_id != null`, OR document it as intentional ("hide-during-loading is preferable to flash-then-disappear for canonical rows"). The Implementer can pick.

- **[MIN-5]** Drizzle snapshot is stale — `supabase/migrations/meta/_journal.json` only tracks through 0003. Migrations 0004-0010 are hand-written and the snapshot was never rebuilt. Designer's claim "the next `npm run db:generate` after the migration would emit a no-op diff" is unverifiable without rebuilding snapshots — generate would emit a huge regression diff for every migration after 0003. The intent (update `schema.ts` to match the hand-written 0011 migration so a future contributor doesn't accidentally regenerate-and-revert) is correct; the "no-op diff" verifiability claim overstates what's testable. **Suggested fix**: drop the "no-op diff" claim from design-v1.md's reasoning around U3. Keep the schema.ts edit (still the right move); reframe rationale as "manual schema-as-code parity with the hand-written migration".

- **[MIN-6]** Helper module path `tests/e2e/_helpers/canonical-exercise.ts` introduces a new directory `_helpers/` with no precedent in `tests/e2e/`. That's fine (the design names it as a new module), but Playwright's `testDir` glob may pick up `.ts` files there as tests if not excluded. Verify `playwright.config.ts` either matches only `*.spec.ts` (the convention in this repo) or excludes `_helpers/`. **Suggested fix**: confirm `playwright.config.ts` has `testMatch: /.*\.spec\.ts/` (or equivalent) so the helper module isn't auto-discovered as a test. If not, add a one-line exclude. Implementer-actionable.

- **[MIN-7]** `scripts/create-user.ts` cosmetic fix is in scope but scope-creep-adjacent. Not a blocker; the design's justification (debugger-trap avoidance) is reasonable. Note that the script currently uses `count: "exact", head: true` — the design's "replace the count with two counts" should preserve that pattern so the diff stays minimal. **Suggested fix**: Implementer keeps the existing `select("id", { count: "exact", head: true })` shape for both counts. Trivial; flag for the Implementer.

- **[MIN-8]** AC4 in design's test-plan table says "Use the existing create-exercise flow" without naming the spec. `crud.spec.ts:323-329` is the closest fit (already creates an exercise as part of the flow). The MAJ-1 fix should cover this by naming the spec(s) — folding [MIN-8] into [MAJ-1].

## Decision

**go**

Reasoning:

- **Zero blockers.** Migration syntax, RLS policy bodies, trigger replacement, anon-read evaluation, FK preservation, schema-as-code parity intent, persisted-cache invalidation, chip placement + dark mode, edit-screen gating (both pencil at source and read-only at destination), helper signature and call-site coverage — all verified against the cited files. The five-step migration is single-transaction-safe (Postgres semantics + Supabase CLI's BEGIN/COMMIT wrapper, confirmed against `0004` precedent).
- **One major** ([MAJ-1]) carried as known debt: the AC4/AC5/AC7 e2e test contract is under-specified. The design names the rls.test.ts arms in full and rewrites seed-and-auth.test.ts in full, but defers the visual "chip renders / pencil absent / read-only deep-link" e2e spec body to Tester discretion. This is recoverable in the Implementer/Tester rounds — the Implementer can pin the spec body when extending `crud.spec.ts` or creating `tests/e2e/canonical-exercise-gating.spec.ts`, and the Tester round will catch any gap — but it's worth flagging as a contract-clarity miss the design should ideally have nailed down. **Not a blocker** under the playbook's rule (0 blockers + ≤1 major = go).
- **Six minors** ([MIN-1] through [MIN-7], [MIN-8] folded into [MAJ-1]): internal contradiction on `useForm` mounting (MIN-1) is the most likely to confuse the Implementer; the others are cosmetic, documentary, or Implementer-handleable. None are blockers.

Recommendation: **invoke Implementer**. Forward this validation file so the Implementer disambiguates MIN-1 explicitly (useForm stays mounted, no hook-order violation) and pins the e2e spec body for AC4/AC5/AC7 per [MAJ-1] when writing the implementation plan. The Tester round will then have a concrete assertion list to execute rather than designing tests from scratch.
