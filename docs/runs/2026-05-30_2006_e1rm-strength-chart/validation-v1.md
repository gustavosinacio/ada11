## Explicit verdict on the 3 flagged items

**(1) LOCF untrained-week treatment (Decision #7a, R-3) — CONFIRMED sound.**
- (a) `<MultiSeriesChart>` has NO gap support — every `values[]` entry is rendered as a polyline vertex AND a dot (`multi-series-chart.tsx:134-160`), y-min pinned to 0 (`:81`). A zero-fill on a rest week WOULD crash the line to the x-axis and back. The design's premise is FACT, not speculation.
- (b) The §4-step-6 algorithm produces a fully-numeric array. Walk-forward LOCF leaves leading `null`s only before the first real value; the explicit "replace every leading null with the first non-null value" pass eliminates them. **No null survives** — because eligibility (step 4/5) guarantees ≥1 real cell, the first-non-null lookup always succeeds. I traced the index-0 edge: if the first real week is index 0, `values[0]=cellMax` on the first iteration, `last` is set, and there are zero leading nulls to replace — no off-by-one, no leading 0. Correct.
- (c) Flat-hold is semantically defensible for a peak/"most-recent-capability" metric (a rest week is not strength=0); the named trade-off (long gap overstates current strength) is correctly accepted and scoped out. This is the standard LOCF treatment for sparse strength logs.

**(2) Eligibility-before-ranking (Decision #2, R-4) — CONFIRMED sound.**
- Step 4 adds `row.session_id` to `sessions[exercise_id]` and marks `eligible` ONLY on guard pass (`w>0 && r>0`). A bodyweight-only exercise (all rows `weight=0`) never passes the guard → its `sessions` set stays empty / it is never marked eligible → step 5 ranks ONLY eligible exercises. A high-frequency bodyweight-only movement therefore CANNOT consume a top-N slot for an invisible line. The trace is airtight: ineligible exercises never reach the ranking. R-4 is mitigated by construction.

**(3) Invariant D + E1 fidelity (R-1, R-2) — CONFIRMED faithful and unambiguous.**
- Contract uses LOGGED weight (`w = row.weight ? parseFloat(row.weight) : 0`, guard `w>0 && r>0`) — matching `progress.tsx:155-159`, NOT `effectiveWeightKg`. MAX-into-cell, NOT `+=` — diverging from `weekly-muscle-volume.ts:112`. The "What is NOT in this algorithm" block (`design:210-215`) explicitly forbids `effectiveWeightKg`, `measurements`, `+=`, and zero-fill, and §F2 omits `useMeasurements` entirely. **A copy-paste of the muscle presenter is structurally precluded**: it would need a `measurements` arg the contract refuses to accept, and the unit cases #3/#4/#7/#10 assert MAX-not-sum and no-bodyweight-line. The contract is unambiguous enough that the Implementer cannot accidentally copy the volume path. This directly closes last run's MAJ-2 (the shared-`const w` corruption) — here the new presenter has its OWN loop, so no shared-variable coupling exists.

### Majors
- **[MAJ-1]** `design-v1.md:282` (E2E case #4, the NEGATIVE / Invariant-D-end-to-end test): the assertion `getByText("Estimated 1RM per exercise").toHaveCount(0)` has **no positive anchor awaited first**, so it can fire before the page hydrates and pass spuriously (false green). For the bodyweight-only user the entire section is `return null` AND the section is ALSO null while `isLoading` — there is no "section appeared then is absent" transition to wait on. `gotoProgress` only waits for `networkidle` (`weekly-muscle-volume.spec.ts:155-158`), which does not guarantee React Query has resolved `useLifetimeWeeklyVolume` + `useAllExercises` and the page has re-rendered. The positive cases (#1-#3) are safe because they `await expect(header).toBeVisible()` first; case #4 is the ONE test proving the feature's core invariant (no e1RM line for bodyweight) and it is the one without a settle-gate. This is the runtime-semantics gate lesson from my feedback file applied to a negative assertion. **Suggested fix**: before the two `toHaveCount(0)` assertions, await a reliably-present Progress-page anchor for a settled-but-empty page — e.g. `await expect(page.getByText("Streak").first()).toBeVisible()` (`<StreakCard>` always renders its "Streak" header or "Finish a session this week…", `streak-card.tsx:44,48`), OR seed the same user with a SECOND weighted exercise that DOES plot and assert that line is visible first, then assert the Push-up line has count 0. The settle-gate must be explicit, not implicit in `networkidle`.

- **[MIN-2]** `design-v1.md:204-206` (LOCF pseudo-code) under `noUncheckedIndexedAccess: true` (`tsconfig.json:5`): the `cell[id][w]` / `values[w]` indexing will require the non-null-assertion idiom the muscle presenter already uses (`weekly-muscle-volume.ts:109,112` `values[idx]!`). The pseudo-code omits the `!`/undefined-guard, and "is a real number" must be implemented as an explicit `!== undefined` check (a sparse `(number|undefined)[]` cell distinguishes unset from a real value — safe because a passing guard never yields 0). **Suggested fix**: note in the contract that the cell is `(number|undefined)[]` (or a `Map<weekIdx,number>`) and that the realness test is `cell[w] !== undefined`, mirroring the established `!` idiom — purely an implementation note so the Implementer doesn't reach for `cell[w] > 0` (which would also work but is less explicit) or trip the linter.
