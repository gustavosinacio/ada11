## Issues found

### Blockers
- None. (MAJ-1 below is severe — it breaks the owner's pre-confirmed canonical-kernel invariant — but it is design-recoverable in v2 and does not crash, so it is classified major per the playbook severity definitions.)

### Majors

- **[MAJ-1]** `history/week/[isoWeek].tsx:82-93` (missing from design kernel inventory `design-v1.md:330-348`): The week drill-down **headline volume** (`weekVolumeKg`) is a 14th independent inline `w*r` kernel over `WeeklyVolumeRow[]` that the design did NOT enumerate and does NOT fix. It also feeds `avgVolumePerSession` (`:107-108`, displayed `:163,172`). If left unfixed, a bodyweight exercise's week headline + average will diverge from (a) the per-session row totals on the SAME screen (`groupSessionVolumes`, `:99` — which IS fixed), (b) the weekly strip bar, and (c) the new per-muscle chart — directly violating the owner's pre-confirmed "same volume number everywhere" decision (`state.md:7,58`). Discovery flagged the prompt missed 2 sites and found them; the Designer missed a 3rd despite that warning. **Required fix:** add `history/week/[isoWeek].tsx:88` to the kernel-site inventory; route `weekVolumeKg` through `effectiveWeightKg(row.exercises.equipment, row.weight, bodyweightKgAsOf(measurements, parseISO(row.sessions.started_at)))` memoised per session; mount `useMeasurements` on the screen; add the screen to the wiring table. Re-grep `* r` / `parseFloat(...weight)` to confirm no 15th site (I found none beyond this — see verification).

- **[MAJ-2]** `app/(app)/exercises/[id]/progress.tsx:138-147` (design file-change row `design-v1.md:47` contradicts its own stated invariant): The screen computes e1RM and volume in ONE loop sharing a single `const w` under one guard `if (w > 0 && r > 0)` (`:142`). The design says "e1RM stays computed from logged weight… only the `sessionVolume += w*r` line uses effective weight" (`:47`, and Out-of-scope `:383`) — but the instruction it actually gives ("replace `const w = set.weight ? parseFloat(set.weight) : 0`") would (a) feed effective bodyweight into `epley1RM(w, r)` at `:143`, silently making e1RM bodyweight-aware, and (b) change the e1RM inclusion guard so a `weight=0` bodyweight set with `bw>0` now produces an e1RM point at `epley1RM(bodyweight, reps)`. This is a latent cross-surface inconsistency the design explicitly says it does NOT want. **Required fix:** the design must specify a two-variable split: keep `const w = set.weight ? parseFloat(set.weight) : 0` driving `epley1RM` and the e1RM guard `w > 0`; introduce a separate `const effW = effectiveWeightKg(equipment, set.weight, bw)` driving `sessionVolume += effW * r` under its own `effW > 0` guard. State explicitly that the e1RM guard and the volume guard diverge for bodyweight sets (a Pull-up logged `weight=0` produces volume but NO e1RM point).

### Minors

- **[MIN-1]** `computeVolumeTarget` (`design-v1.md:38` vague vs `:194` contract; code at `volume-target.ts:177-190`): the file-change row only says "uses effectiveWeightKg in the currentWeightKg reduce." There are THREE spots that must change consistently or a bodyweight set breaks: the `> 0` gate (`:179`), the displayed `currentWeightKg` extraction (`:184-186`, currently `parseFloat(currentSet.weight)` → would be `0` for a Pull-up), and the `repsToBeat` denominator (`:187-190`). The contract at `:194` is right; the implementation instruction should enumerate all three so the Implementer doesn't leave `currentWeightKg` as raw logged weight. Suggested fix: state "the displayed `currentWeightKg`, the selection gate, and the `repsToBeat` denominator all use `effectiveWeightKg(...)`."

- **[MIN-2]** F-4 justification (`design-v1.md:19,355`): the stated reason "fixtures use barbell exercises" is inaccurate — 4 volume specs use `pickCanonicalExercise(admin)` with no preferred name, taking the alphabetically-first canonical row (could be a bodyweight exercise). The conclusion (numbers don't move) is correct, but for the right reason: no spec seeds `measurement_entries`, and sets carry explicit positive weights, so `bodyweightKgAsOf → null → effective = addedLoad`. Suggested fix: restate the F-4 invariant the Tester must audit as "no volume spec seeds a measurement_entries row AND all seeded sets carry explicit positive weight" rather than "exercises are barbell." If a future spec adds a measurement fixture for a bodyweight pick, numbers WILL shift.

- **[MIN-3]** Wiring prose for `WeeklyVolumeRow` hooks (`design-v1.md:57`): says to build `{ measurements, equipmentByExerciseId }` from `useAllExercises` for `useLifetimeBestWeek`/`useCurrentWeekVolume`/`usePrsThisWeek`. But per the design's own `progress-page-math.ts` change (`:39`), those WVR kernels read equipment from `row.exercises.equipment` (the widened SELECT) and take only `WeeklyBodyweightInput = { measurements }` — NOT an `equipmentByExerciseId` map. Only `useExercisesThisWeek`'s inline `nowKg` reduce (`:251`) and the per-exercise screen use a lib-derived equipment lookup. The prose conflates the two paths. Suggested fix: clarify that WVR kernels need only `useMeasurements` added (equipment arrives on the row); `useAllExercises` is needed only where the SetRow/SessionSets path or the muscle-join is in play.

- **[MIN-4]** Test fixture migration (`tests/unit/weekly-volume-bucketing.test.ts:17,24-36`): making `WeeklyVolumeRow.exercises` a required field will break `buildRow` (constructs the row literal) AND its `RowInput` `Omit` type (line 17 omits `set_type|exercise_id|session_id|sessions` but not `exercises`, so callers would be forced to pass it). Design (`:82`) anticipates the default but not the `Omit`/`RowInput` edit. Suggested fix: note that `RowInput` must add `exercises?` and `buildRow` must default `exercises: { equipment: "barbell" }`. Same applies to any other fixture building `WeeklyVolumeRow` literals (`progress-page-math.test.ts` `mkRow`, `session-verdict-math.test.ts`).

- **[MIN-5]** Per-set-sum invariant (`exercise-session-row-format.ts:72-73`): the in-code comment guarantees `sum(presentSetVolumeLines) === sumPastVolume(sets)`. After the change this holds ONLY if `presentSetVolumeLines` and `presentExerciseSessionRow` receive the IDENTICAL `equipment` + `bodyweightKg`. The design wires both (`:59-60`) but does not state the invariant as a regression assertion. Suggested fix: add to the Regression contract that the Tester asserts per-set lines still sum to the session total for a bodyweight exercise.

## Decision

**no-go**

Reasoning (round 1 of 3 Design↔Validate):
- 0 blockers, **2 majors** → no-go per the playbook rule ("2 or more majors → no-go").
- The design is otherwise strong: F-1 (the most correctness-critical claim) is fully verified and complete; the `!inner` safety is provably correct (FK `restrict` + deleted_at-agnostic RLS); the `effective > 0` byte-identity holds across all edge cases; the fallback rule, plumbing seam, and Phase 1 chart decisions are sound; F-5 removal is clean.

Re-confirm via grep that the inventory is now exhaustive (Validator found exactly this one missed site — no 15th).
2. **[MAJ-2]** Replace the per-exercise screen instruction with an explicit two-variable split (`w` for e1RM under `w>0`; separate `effW` for volume under `effW>0`), and state that for a bodyweight set the volume and e1RM guards intentionally diverge.
3. Address MIN-1 (enumerate all three `computeVolumeTarget` spots), MIN-2 (restate F-4 invariant as "no measurement fixture + explicit positive weight"), MIN-3 (don't over-specify `equipmentByExerciseId` for WVR hooks), MIN-4 (`RowInput`/`buildRow` fixture edits), MIN-5 (per-set-sum regression assertion) — minors, fold in where cheap.
