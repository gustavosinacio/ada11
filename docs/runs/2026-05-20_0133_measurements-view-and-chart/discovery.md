# Discovery — 2026-05-20_0133_measurements-view-and-chart

## Feature prompt

Bundles two backlog items from `docs/features.md:4-5`:

1. "when clicking on the measurements, we should see a screen to view what was measured, and then go to the edit measurements when i press an 'Edit' button" — split the current tap-to-edit flow into **tap → view → Edit button → edit**.
2. "measurements screen should show a graph to represent progress" — add a chart visualizing measurement history.

Both touch the just-shipped Measurements vertical (`docs/runs/2026-05-19_2353_measurements-tracking/final-summary.md`). Bundling is sensible: the routing split (#1) is small, the chart (#2) is small, and both live in the same folder.

## Scope summary

Two surgical changes to the Measurements feature, no schema work, no new tables, no new API methods. (#1) Restructure routing so that tapping a list row lands on a read-only **view** screen showing every filled metric in a friendly layout, with an "Edit" affordance that pushes the existing edit form. (#2) Add a single line chart on the measurements list screen visualizing **bodyweight** over time (the one universal metric every entry has), modeled on the `WeeklyVolumeStrip` precedent that already sits as `ListHeaderComponent` on the History tab. Both reuse `useMeasurement` / `useMeasurements`, `ProgressChart`, `formatWeight`, `formatLength`, and the existing nested-dynamic-route precedent at `app/(app)/exercises/[id]/`.

## Relevant conventions (verified by reading code)

- **Routing** — Expo Router file-based. `app/(app)/measurements/_layout.tsx:3` declares a `Stack` with `headerShown: false`; per-screen titles come from `<Stack.Screen options={{ title: ..., headerShown: true }} />` rendered inside each screen (e.g. `[id].tsx:178-180`). Nested dynamic routes use folder form: `[id]/index.tsx` for the base, `[id]/<sub>.tsx` for siblings. Verified at `app/(app)/exercises/[id]/`. The file-`[id].tsx` + folder-`[id]/` cannot coexist at the same segment.
- **Deep-link path style** — both `router.push("/(app)/measurements/${id}")` with the route group prefix (`measurements/index.tsx:80`, `[id].tsx:145`) and `<Link href={\`/exercises/${id}/progress\`}>` without the group (`exercises/[id]/index.tsx:185`) are used in the codebase. Either is valid; Expo Router normalizes the group. The `router.push` form is the dominant pattern for callbacks; `<Link>` for declarative buttons.
- **List-row pressability** — `Pressable` with `accessibilityRole="button"` and `active:bg-gray-50 dark:active:bg-gray-950` for tap feedback (`measurement-list-item.tsx:56-59`). A `ChevronRight` cue on the right edge is the convention to indicate "this navigates" (`measurement-list-item.tsx:75`).
- **Screen headers** — every screen mounts a `<Stack.Screen options={{ title: "...", headerShown: true }} />`. Header actions (e.g. `+`) go in `headerRight` (`index.tsx:30-39`). An "Edit" affordance on a view screen would most naturally live in `headerRight`, mirroring the `+` precedent. A button-styled CTA inside the ScrollView is the alternate (`exercises/[id]/index.tsx:185-194` "View progress" button) — both are codified.
- **Loading / error / empty / data quadrant** — universal four-branch render: `ActivityIndicator` (loading) → red error text (`error.message`) → empty-state with CTA → content. Verified at `measurements/index.tsx:43-87` and `[id].tsx:148-170`.
- **Sectioned content** — uppercase section headers via the inline constant `SECTION_HEADER = "mt-4 mb-2 text-sm font-medium uppercase text-gray-500"` (`[id].tsx:38-39`, `new.tsx:25-26`). The view screen should reuse this exact class for visual consistency with the edit form.
- **Unit-aware formatting at the UI boundary** — `weight_kg` and `*_cm` columns are stored as canonical kg/cm strings (`db/types.ts:132-141`); the UI converts at render via `formatWeight(parseFloat(weight_kg), unit)` (`measurement-list-item.tsx:25-27`) and `formatLength(parseFloat(neck_cm), unit)` (`measurement-list-item.tsx:33-35`). Body-fat is the only non-converted metric — rendered as `${n.toFixed(1)}% bf` (`measurement-list-item.tsx:29-31`).
- **Query invalidation** — write paths invalidate `["measurements"]` for the list and `setQueryData(["measurements", id])` for detail cache (`use-measurements.ts:36-52`). The new view screen reads `useMeasurement(id)` which already hits the detail cache populated by the list query indirectly via `qc.invalidateQueries`; navigation from list → view should feel instant.
- **Date formatting** — list row uses `format(parseISO(entry.measured_at), "EEE, MMM d, yyyy")` (e.g. "Wed, May 20, 2026") at `measurement-list-item.tsx:49`. The view screen should reuse this format for the headline date. Edit/new forms display `YYYY-MM-DD` as a raw input (`[id].tsx:188`, `new.tsx:121`).
- **NativeWind tokens** — black-and-white aesthetic with `bg-white dark:bg-black`, accents in `text-blue-500` (chart polyline, view-progress link), borders `border-gray-200 dark:border-gray-800`, dividers `border-gray-100 dark:border-gray-900` for tighter list rows.
- **Component file-naming** — kebab-case feature/object-noun pairs: `measurement-list-item.tsx`, `weekly-volume-strip.tsx`, `session-summary-row.tsx`, `progress-chart.tsx`. The new chart component should follow: e.g. `measurements-progress-strip.tsx`.

## Constraints

- **Data**: No schema change. No new RLS work. Reads only — `listMeasurements` (`api/measurements.ts:100-108`) and `getMeasurement` (`110-119`) are sufficient for both features. The chart filters `weight_kg != null` and excludes rows missing the primary metric; no DB-side filtering needed because `~50 entries/year/user` (per task brief) makes client-side filtering trivial. No FK relations to consider.
- **UI**:
  - Routing must respect Expo Router's segment-collision rule: `[id].tsx` and `[id]/` cannot coexist. Pattern A requires deleting (or rather, replacing) the current `[id].tsx` file when adding the folder.
  - `<Stack.Screen options={{ title }} />` inside each screen controls the header per-screen; the parent stack at `measurements/_layout.tsx:3` is silent. Both view and edit will set their own titles.
  - Chart on the list screen must coexist with the empty-state branch (`index.tsx:55-70`) which short-circuits the FlatList. Strip precedent at `weekly-volume-strip.tsx:87-89` returns `null` on no-data, which works because the FlatList itself only renders when there is at least one row. Designer must decide whether to hide the chart in empty-state or render it above a CTA — but precedent says hide.
- **Platform**: `react-native-svg@15.12.1` (`package.json:57`) renders on iOS, Android, **and** web. `ProgressChart` is already in production on the web build (used by `exercises/[id]/progress.tsx`). No platform divergence expected. `useWindowDimensions()` works on all three (precedent at `progress.tsx:26`). Header buttons via `headerRight` render in the native stack header on iOS/Android and in the web stack header — both supported.
- **Auth**: Existing `auth.uid()` RLS on `measurement_entries` already covers all reads. No new auth context.
- **Performance**:
  - List → view → edit chain hits the TanStack cache. The list query populates `["measurements"]`; `useMeasurement(id)` then makes its own detail query for `["measurements", id]`. The detail query is **not** prefilled from the list, so the view screen will show a brief loading spinner on first navigation unless we either (a) hydrate the detail cache from the list (mirror what `useCreateMeasurement.onSuccess` does at `use-measurements.ts:39`) or (b) accept the spinner. **Recommendation**: hydrate detail-from-list in `useMeasurements`'s `onSuccess` or via `qc.setQueriesData` in a `select` — but designer call. Status quo without hydration is acceptable for <100 rows.
  - Chart: pure client-side derivation, `useMemo` on `entries`. With 50 points the SVG rendering cost is negligible. No virtualization needed.
- **Accessibility**: `accessibilityRole="button"` on every tappable element (`measurement-list-item.tsx:58`, `[id].tsx:378-380`). The new Edit button must follow. `accessibilityLabel` is used for icon-only buttons (`index.tsx:33`). Chart axis labels are `<SvgText>` — not a screen-reader-friendly representation, but matches existing `ProgressChart` accessibility floor (not raised in scope).

## Existing precedents

- **Folder-style nested dynamic routes**: `app/(app)/exercises/[id]/{index.tsx,progress.tsx}` is the closest precedent for the routing split. Pattern A is mechanically a copy of this layout. Implementer should mirror file boundaries.
- **`ListHeaderComponent` strip above a list**: `app/(app)/history/index.tsx:48` mounting `<WeeklyVolumeStrip />`. The chart on the measurements list is structurally the same component class as the weekly volume strip, just one line series instead of bar chart. Same mount pattern; reuse the `useMemo` + early-`null` branches.
- **Read-only summary screen with sectioned metrics**: there is **no** existing read-only view screen in the codebase. Every detail screen today is an edit form (`exercises/[id]/index.tsx`, `routines/[id].tsx`, `history/[id].tsx`, `measurements/[id].tsx`). The new view screen is structurally net-new for the project. Closest visual cousins are `session-summary-row.tsx` (a list row, not a full screen) and the form-without-inputs sections in `[id].tsx:198-355` (which the designer can borrow as a read-mode rendering by swapping `Input` for `Text` rows).
- **Header-right action button**: `index.tsx:30-39` (the `+` button for new). Models the "Edit" header-right button on a view screen if the designer chooses header placement.
- **Inline "deep-link to related screen" button**: `exercises/[id]/index.tsx:185-194` — bordered blue `Pressable` "View progress". Inverse direction model for an "Edit" button styled as a body CTA. Note: this precedent uses `<Link href asChild>` + `<Pressable>`, while most navigations elsewhere use `router.push()`. Either works.
- **Empty / single-point chart fallback**: `progress-chart.tsx:59-77` — `length === 0` shows "No data yet"; `length === 1` shows a big number with the single date label. Already handles the < 2 datapoints case the designer must address (Unknowns §8).

## Unknowns (require Designer judgment or human decision)

1. **Routing pattern (A vs C; B is mechanically invalid).** Pattern A (folder-style, `[id]/index.tsx` view + `[id]/edit.tsx` edit) matches the existing `exercises/[id]/` precedent and is the recommended path. Pattern C (single file with view/edit mode state) avoids file moves but loses URL-level addressability of edit mode. **Assumption (MEDIUM confidence)**: Designer picks Pattern A.
2. **View-screen layout.** Three styles plausible: (a) flat list of label → value rows mirroring the edit form's section headers (Weight & body fat / Upper body / Core / Lower body / Notes), with rows hidden when the metric is null; (b) compact card grid (2 columns) of metric chips, skipping nulls; (c) headline metric stack (date, weight, body-fat) at top + collapsible detail. Edit form's section structure (`[id].tsx:198-355`) is the obvious template — reuse the same `SECTION_HEADER` class and section order, swap `Input` rows for two-line `Text` rows (label + value). **Recommendation**: (a) for consistency with the edit form, hide null rows entirely.
3. **Chart placement.** Three plausible spots: (a) **top of list screen** as a `ListHeaderComponent` strip (matches Weekly Volume Strip precedent, matches the literal prompt "measurements screen should show a graph"); (b) **on the view screen** with per-metric context (less aligned with the prompt); (c) **dedicated `measurements/chart.tsx` screen** linked from the list (heavyweight). **Recommendation**: (a) — strongest evidence in both the prompt wording and the WeeklyVolumeStrip precedent.
4. **Which metric(s) does the chart show?** Options: (a) bodyweight only — single fixed metric, simplest, universally populated; (b) per-metric chip toggle above the chart (cycle through weightKg, bodyFatPct, waistCm, etc.); (c) multi-chart grid, one chart per metric that has ≥ 2 datapoints. Bodyweight is the only universal — every entry has a weight (well, technically nullable too, but it's the most-filled in practice). Multi-grid risks scroll fatigue. **Recommendation**: start with (a) bodyweight only, leave hooks for (b) chip-toggle in a follow-up if the owner asks.
5. **Chart x-axis range.** All entries / last N entries / last N weeks / last N months. The `ProgressChart` x-label thinning at `progress-chart.tsx:53` keeps the axis legible at ~50 points. Edge case: very long histories (years) make the chart compressed. **Recommendation**: all entries for v1; designer may cap at last 26 weeks or last 50 entries if the owner has strong opinions.
6. **Delete button placement.** Currently lives on the edit screen (`[id].tsx:415-422`) inside a `mt-6 border-t` separated section, guarded by `confirmDelete`. Question: stays on edit only (designer recommends keeping it there per the task brief), moves to view (faster but riskier), or appears on both. **Recommendation**: keep on edit only; the prompt does not mention delete and accidental delete from a view-only screen is a UX foot-gun.
7. **Duplicate-banner target post-split.** Both `new.tsx:103` and `[id].tsx:145` (the "Open existing entry" button) `router.replace` to `/(app)/measurements/${row.id}`. Post-split this resolves to the view screen under Pattern A. But the banner's text ("edit it instead?", `new.tsx:312-314` and `[id].tsx:374-376`) implies the user wants to land in edit mode immediately. Options: (a) keep banner text and route to view; (b) keep route to view, change copy to "view it instead?"; (c) route to edit (`/(app)/measurements/${row.id}/edit`) to honor the existing copy. **Recommendation**: (c) — route directly to edit, since the banner is a corrective flow ("I tried to log today twice, take me to the existing one to fix it"). The view-detour adds friction in a flow that's already a recovery path.
8. **Empty-state for the chart.** `ProgressChart` already gracefully handles `length === 0` (returns a "No data yet" note) and `length === 1` (renders a big-number card). For the strip mount: when there are 0 or 1 weight datapoints, render the strip as `null` (matches WeeklyVolumeStrip's "no chrome on empty data" behavior, `weekly-volume-strip.tsx:87-89`), or show the strip with the chart's built-in fallback. **Recommendation**: `null` on `weight_kg`-bearing-entry-count < 2 — keeps the list clean.
9. **Header chrome on the view screen.** Title options: static `"Measurement"`, dynamic `"May 20, 2026"` (the entry's date), or hybrid `"Measurement · May 20"`. The edit screen uses the static `"Edit measurement"` (`[id].tsx:179`). **Recommendation**: static `"Measurement"` for symmetry with `"Edit measurement"` and to avoid date-format conditional logic in the header.
10. **Native-vs-web parity for the Edit button.** Both headerRight and inline-CTA placements render fine on both. Designer call on which feels right; the inline CTA gives more visual weight (full-width bordered Pressable) while headerRight is the iOS-native idiom.
11. **Chart sub-extraction.** Is the chart logic worth extracting from the strip component into a pure helper at `src/utils/measurements-chart.ts`? Mirrors the `computeStripModel` extraction in `weekly-volume-strip.tsx:34-60` (which the validator MIN-2 enforced last run). For testability and consistency with the prior run's standard, **recommendation**: yes — extract `entriesToWeightSeries(entries, unit) → DataPoint[]` to a util file.
12. **Hydrating detail cache from list.** On first navigation list → view, the `useMeasurement(id)` query runs from scratch even though the row data already exists in the `["measurements"]` cache. Option: in `useMeasurements`'s success, fan-out `qc.setQueryData(KEYS.detail(row.id), row)` for each row. Mostly a polish item — view screen will show a brief spinner without it. **Recommendation**: ship without hydration; revisit if perceptible flicker.
