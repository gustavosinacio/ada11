# Discovery — 2026-05-22_1300_pr-context

## Feature prompt

> "PRs this week" needs to show WHICH PRs + better in-app context for the numbers in general.
>
> - The Progress page hero shows `+N PRs · Y · Z` but doesn't surface which exercises hit a PR. Either (a) make the PR count tappable → expands a list of "this week's PR rows" (exercise + new max + previous max), or (b) add a dedicated "PR'd this week" section above the per-muscle list, or (c) tag PR rows in the per-muscle list with a distinct visual treatment. Designer picks. The verdict screen already shows a similar list for the just-finished session — Progress should show the cumulative this-week version.
> - Broader UX: review the screens for places where numbers are surfaced without context (e.g., "Volume to PR: 4,900 kg" — what does that mean to a user who hasn't seen the per-exercise live strip? "Max · Now · To PR" — what's "Now"?). Add inline copy / labels / a brief help affordance where helpful. Designer call on scope; minimum bar = the Progress hero PR section.

(Date: 2026-05-22 BRT. Verified — system clock advanced from 05-19 to 05-22 inside the session; doesn't affect any "this week" semantic in this discovery.)

## Scope summary

Touches the Progress tab's PR-surfacing and the project-wide ambiguity around the `Max · Now · To PR` triplet. Two related concerns: (1) the **Hero** at the top of `app/(app)/progress/index.tsx` shows the count of PRs this week but no exercise names; (2) the `Max · Now · To PR` line, rendered in three surfaces (hero, per-muscle list rows, live-workout strip), lacks a one-shot in-app explainer of what each number means. The verdict screen already implements a celebratory PR-row pattern (`{exercise} [PR] / +X kg (was Y kg)`) that the Progress page can either reuse, factor out, or independently match. Everything is client-side derived — no DB / API changes are required (verified: `computePrExerciseIdsThisWeek` already returns the set of PR'd exercise ids).

## Constraints

- **Data**: no schema changes needed. The lifetime read `useLifetimeWeeklyVolume` (`use-stats.ts`) already returns every set's `weight`, `reps`, `exercise_id`, `session_id`, `completed_at`, `sessions.started_at`. All math runs in-browser. RLS untouched — same protected tables (`sets`, `sessions`, `exercises`).
- **UI**: NativeWind classes; no styled-components. Universal-app constraint: must render on web + iOS + Android. Existing modal precedents (`<ChooseActionModal>`, `<ExercisePicker>`, `<PlateCalculator>`) use plain RN `<Modal>` for cross-platform safety. No tooltip primitive exists today (verified by grep — no `Tooltip` / `Popover` / `HelpCircle` import). If Designer wants a hover-tooltip on web, that's a new abstraction.
- **Platform**: iPhone is the primary target (`docs/README.md:18`). Any "hover" tooltip degrades on touch. Tap-to-expand or inline copy is the safer pattern.
- **Auth**: same session-scoped, RLS-protected reads as the existing Progress page. No change.
- **Performance**: the per-exercise priorMax derivation requires walking sessions for each PR exercise. The existing `computePrExerciseIdsThisWeek` already does that walk and discards the priorMax (math kernel:240-249). Capturing it costs O(1) extra memory per PR session. No additional fetches.

The prompt's wording is shorthand. Designer should restate which surface they actually mean (the eyebrow + count IS the hero — there's no "+N PRs" inline in the hero today). 9. **`PR! +X kg (was Y kg)` math semantic for week scope.** For a session-scope PR (verdict), `priorMaxKg = lifetime max excluding the current session`, `currentKg = the single session's total`. For week-scope (Progress), what's the analogue? Options: (i) `priorMaxKg = lifetime max BEFORE this week's first session`, `currentKg = the single best session this week`. (ii) `priorMaxKg = lifetime max excluding ALL sessions in this week`, `currentKg = best session this week`. The two diverge only when the user has multiple sessions for the same exercise THIS week, the earlier of which was already a PR — option (i) prices the priorMax at "before any session this week", option (ii) accounts for the within-week climb. Designer + Validator must pick. Recommend option (i) for simplicity (matches existing kernel's running-priorMax check at `progress-page-math.ts:242`).
