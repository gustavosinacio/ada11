# Discovery — 2026-05-24_1925_history-row-total-volume

## Feature prompt
> Total volume on history session rows. The History tab lists past sessions, currently showing the workout name on line 1 and date/duration on line 2. Add the session's total volume to the row (e.g. "12,345 kg" or "27,210 lbs" depending on user's weight-unit preference). Use the same kernel (`sumLiveVolume`) that drives the live session header + verdict screen + per-exercise live strip so the number is consistent across surfaces. The number should not be inferred from cache derivation that would force a per-row N+1 fetch — derive from the data the session-list query already returns OR add a lightweight aggregation.

## Scope summary
Add a per-session total volume (kg/lbs) to each `<SessionSummaryRow>` rendered by the History list and by the per-week drill-down. The prompt's "no per-row N+1" constraint is satisfied for free: the History screen already loads `useLifetimeWeeklyVolume()` (lifetime non-warmup, `completed_at IS NOT NULL`, finished-session rows with `session_id`) to power `<WeeklyVolumeStrip>`. Grouping that cached dataset by `session_id` yields per-session totals in one client-side reduce — no new query, no new column, no schema change. The kernel predicate is identical to `sumLiveVolume` modulo filters that are already enforced server-side.

## Relevant conventions (verified by reading code)
- **Volume kernel canonicalization.** Every live/verdict/strip volume readout funnels through one of two predicates in `src/utils/volume-target.ts`: `sumLiveVolume` (live session, F10 "checked = committed") or `sumPastVolume` (finished sessions where every set is implicitly committed; warmup-skip + `w>0 && r>0` only). See JSDoc at `volume-target.ts:53-67`. Strip math at `weekly-volume-strip-math.ts:69-77` uses the same `parseFloat(weight) * reps` with `w>0 && r>0` inline (server pre-filters warmups/completed_at).
- **Aggregation pattern (no N+1).** `src/utils/progress-page-math.ts:186-205` already groups `WeeklyVolumeRow[]` by `session_id` to build per-session aggregates. `src/utils/session-verdict-math.ts:33-48` groups by `exercise_id` and reduces each group via `sumLiveVolume`. Both are pure functions; same shape applies here.
- **Display helper split.** `formatVolume` for aggregates (`session-header.tsx:46`, `weekly-volume-strip.tsx:249`, `verdict.tsx:139`, `volume-target-slot.tsx:61-63`, `pr-list-row.tsx:55`, `progress/index.tsx:41-42`, `week/[isoWeek].tsx:154,163`); `formatWeight` for per-set displays (`session-summary-row.tsx:51` is the lone aggregate-using-formatWeight outlier in the row, and `history/[id].tsx:292` mirrors the same outlier in the detail header).
- **In-flight rerenders are budgeted.** `app/(app)/workout/[sessionId].tsx:82-92` notes the rerender cost: the 1-second elapsed-clock tick does NOT recompute volume. Our row has no clock and `data` updates only on refetch, so memoization granularity is a non-issue.
- **Pure-math kernels live under `src/utils/`.** Components import the kernel; routes own data wiring. Tests (e.g. `tests/unit/session-header-total-volume.test.ts`) import the kernel directly.

## Constraints
- **Data**:
  - `sessions` (table): rows include `ended_at IS NULL` for in-progress sessions. Lifetime cache excludes them, so any client-side derivation from the lifetime cache renders `0 kg` for the active session. The current row UI already shows `"In progress"` for `!session.ended_at` (`session-summary-row.tsx:54-58`). Decision needed (see Unknowns): suppress volume on in-progress rows, or fetch the active session's sets and compute live (one extra read, NOT N+1).
  - `sets` (table): `WeeklyVolumeRow` server filters guarantee non-null `completed_at`, non-null `sessions.ended_at`, `set_type != 'warmup'`, `deleted_at IS NULL`. The `sumLiveVolume` kernel's `completed_at != null` and warmup-skip predicates are therefore no-ops over this dataset — but applying the kernel anyway is the right call for consistency (same source-of-truth function across surfaces).
  - `RLS`: lifetime-cache query is already authed; same policy as today (`auth.uid() = user_id`). No new policies needed.
- **UI**:
  - Row currently has 2 lines (name; date · duration), plus a conditional "In progress" 3rd line. Adding volume to line 2 (inline after duration) or line 3 (under date/duration) both feasible — see Unknowns.
  - `FlatList` at `history/index.tsx:45-58` does NOT use `getItemLayout` or fixed `estimatedItemSize`; row height variance is already tolerated (the "In progress" tag adds a line on some rows already). No scroll math to break.
  - Existing aggregate-volume callsites use `formatVolume(volumeKg, unit)` — same helper here.
- **Platform**: web/iOS/Android single codebase; no native divergence implicated.
- **Auth**: `useLifetimeWeeklyVolume` already runs under the authed session; no new context.
- **Performance**:
  - Lifetime read is paginated (1000 rows/page) and cached `staleTime: 60_000`. For a power user with thousands of sets, a single group-by reduce per render is O(n) over the cache (already done by `<WeeklyVolumeStrip>`; one more pass is negligible). The result memoizes on `data` reference identity.
  - Zero new network calls — the data is already loaded for the strip on this exact screen.

## Unknowns (require Designer judgment or human decision)
1. **Layout slot — inline vs new line.** Prompt suggests `· 12,345 kg` appended to line 2. The verdict headline pattern is `+N PRs · Y kg · Zh Wm` (3 items inline). The History row currently has `<date> · <duration>` — appending `· <volume>` keeps the inline rhythm. On iPhone SE 320pt with worst case `Tuesday, May 24, 2026 · 1h 45m · 27,210 lbs`, line 2 likely wraps to 2 visual lines. Two clean options: (a) inline append (let it wrap), (b) move volume to a new explicit 3rd line below date/duration. Designer to decide.
2. **In-progress sessions.** Lifetime cache excludes `ended_at IS NULL`, so deriving from it yields `0 kg` for the active session row. Choices: (a) hide the volume slot when `!session.ended_at` (clean; matches the existing "In progress" semantic — that row already carries an orange tag indicating it's not finished), (b) read `useSetsForSession(activeSessionId)` and run `sumLiveVolume` directly for the active row (1 extra hook for the active row, NOT N+1 over historical rows). Recommendation lean: (a) hide — the "In progress" tag is the user signal.
3. **Empty-state semantics.** A finished session with only warmup sets (or no checked sets, though impossible because Finish bulk-checks; or all soft-deleted via the Finish "discard unchecked" path) computes to `0 kg`. The row component currently *only* renders volume when `totalVolumeKg != null && totalVolumeKg > 0` (`session-summary-row.tsx:50`). Decision: keep that "hide on zero" behaviour (cleanest), or explicitly render `"0 kg"` (could confuse — looks like a bug). Recommend "hide on zero" — matches the existing prop contract.
4. **Aggregation site — component vs. hook vs. utils.** Three placement options:
    - (a) Pure kernel in `src/utils/` (e.g. `computeSessionVolumeMap(rows): Map<string, number>` mirroring `computeLifetimeMaxPerExercise`), invoked from the route once and `Map.get(session.id)` passed per row. Cleanest, testable, no new hook.
    - (b) New hook `useSessionVolumeMap()` wrapping (a) on top of `useLifetimeWeeklyVolume`. Symmetric with `useLifetimeWeeklyVolume`. Adds indirection for marginal benefit.
    - (c) Inline reduce inside the History route. Cheapest but loses test surface and re-implements at the drill-down site.
   Recommend (a) — kernel under `src/utils/session-volume-map.ts` (or co-locate in `volume-target.ts`), single import for both `history/index.tsx` and `history/week/[isoWeek].tsx`.
5. **Helper alignment in the row.** Should the implementation also fix the existing `formatWeight` → `formatVolume` outlier at `session-summary-row.tsx:51`? Treating "12,345 kg" (prompt verbatim) as authoritative implies yes. The `history/[id].tsx:292` detail header also uses `formatWeight` for an aggregate — same fix? Recommend: align both as part of this feature (small blast radius, semantically correct, the prompt names the format).
6. **Drift on `history/[id].tsx` detail totals.** Lines 124-136 compute `totalSets` and `totalVolumeKg` with a *non-canonical* kernel (no warmup filter, no `completed_at` gate, no `w>0 && r>0` guard). Should this feature also align the detail header to the shared kernel, or is that explicitly out of scope? The prompt names "live session header + verdict screen + per-exercise live strip" as the surfaces to match — it does NOT name the history-detail header, so strictly out of scope. Flag to Designer: there's a real inconsistency in the codebase that this feature will *highlight* (list row shows kernel-correct value; detail header shows kernel-incorrect value when the user taps in). Recommend folding the detail header fix in.
7. **E2E selector update.** `tests/e2e/exercise-progress-ia.spec.ts:294-298` uses the row's "· Nm" duration pattern as the unique locator for the just-finished session row. Adding "· 12,345 kg" after duration does NOT break the existing regex (`/·\s*\d+m\b/` matches against the duration token alone), but the inline comment at line 295 ("the list page doesn't pass totalSets to SessionSummaryRow, so there's no 'N sets' text") becomes stale. Implementer should update the comment to reflect the new "· duration · volume" shape.
