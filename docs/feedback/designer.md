### Lessons for next run
- **NEVER ship a design with two code blocks that contradict each other.** MAJ-1 (`design-v1.md:509-553`) was a "Refinement (cleaner)" subsection that introduced a SECOND map name (`routineSetIdToNaturalKey`) while step 4 still showed the first one (`parentNaturalKeyByRoutineSetId`) being populated in a half-written loop with a comment `"actually we capture this in pass 0..."`. Before submitting, re-read every pseudo-code block end to end and confirm: single canonical algorithm, single map name, no dead variables, no "see refinement below" pointers. The v2 fix (`design-v2.md:711` "What is NOT in this algorithm") is the right shape — adopt it as a default footer for any multi-step algorithm.
- **UX policy choices need explicit weighing of the failure surface.** MAJ-2 (silent seed-failure policy = log+proceed) was a Designer call with no explicit weighing of "what does the user see when this fails?" - **Natural-key claims must be enforced at the DB level.** MAJ-3 (`validation-v1.md:29, 43`) — the seed's `(exercise_id, set_number)` natural key assumed "one routine_exercise per (routine, exercise)" was an invariant, but the only enforcement was a picker-level `excludeIds` UI filter that admin-seed and soft-delete-re-add paths could circumvent. **Before relying on a natural key, search for the DB-level constraint that enforces it; if none exists, either add one in the same migration (v2's choice — partial-unique on `(routine_id, exercise_id)`) OR document that the design tolerates duplicates and tighten the algorithm accordingly.** Hope-based invariants are not invariants.
- **Validator's verification table in v1 (`validation-v1.md:7-29`, 22 claims) is worth pre-reading.** Designer can self-audit by walking the same shape against their own draft before submitting — "for every load-bearing claim I just made, can I cite the file:line that proves it?" - **Sustain the "13 alternatives rejected" discipline** (`design-v1.md:654-680`) — this is the densest section of the design and it carried forward verbatim into v2. Validators and Reviewers cross-check rejection reasoning against the design's other commitments; the more alternatives surface explicitly, the harder it is for a hidden trade-off to slip through.
